# Скорость

## 1. Бюджеты

| Метрика | Цель | Как мерить |
|---|---|---|
| LCP (телефон) | ≤ 2,5 с | Lighthouse mobile по HTTP/2, медиана 5 прогонов |
| CLS | < 0,1 (цель 0) | там же |
| TBT | < 200 мс | там же |
| JS первой загрузки | ≤ 200 КБ gzip | `.next/diagnostics/route-bundle-stats.json` → `firstLoadChunkPaths`, сжать gzip -9 |
| Доступность (Lighthouse) | ≥ 95 | там же |

Google считает LCP хорошим, если он ≤ 2,5 с у 75% реальных посещений (web.dev/articles/lcp). Лабораторный замер — ориентир, полевые данные появятся только с трафиком.

## 2. Приёмы, которые сработали (ARCLINE)

| Приём | Эффект |
|---|---|
| Шрифты: 1 файл-подмножество на семейство вместо 3 срезов, толщины 400–700, без preload | 9 файлов ≈ 200 КБ → 3 файла ≈ 72 КБ; первая отрисовка при реальном замедлении 1,9 → 1,5 с |
| zod не попадает в клиент (константы формы в отдельном файле) | −~90 КБ gzip |
| Окна (проект, кейс, заявка) через `next/dynamic` | JS первой загрузки 279 → 188 КБ gzip (вместе с предыдущим) |
| `content-visibility: auto` для блоков ниже первого экрана + полная раскладка перед переходом по якорю | Первый пересчёт стилей и раскладка — только у первого экрана |
| Фото первого экрана AVIF, качество из `images.qualities` | 36,6 → 29,9 КБ |
| Размытие фона только для мыши, нет scroll-driven анимаций на телефоне | Плавная прокрутка на Android |
| Фото первого экрана: `loading="eager"`, `fetchPriority="high"`, `sizes="100vw"`, без анимации | LCP — сразу фото, без задержки отрисовки |

Итог: LCP по HTTP/2 в симуляции 2,93 → 2,41 с, при реальном замедлении 2,32 → 1,57 с; TBT 909 → 310 мс; вес 623 → 374 КБ.

## 3. Правила `content-visibility`

- Ставь на полноширинные блоки с внутренним отступом (`section.lazy-section > .shell.py-16`): изоляция обрезает рисование по краю блока — тени карточек у края блока шириной `max-w` будут срезаны.
- Не ставь на блоки с `position: fixed` внутри: блок станет опорой для fixed-элементов (мобильная панель итога калькулятора уедет вместе с блоком).
- `contain-intrinsic-size: auto 1500px` — `auto` запоминает реальную высоту после первой отрисовки.
- Перед переходом по якорю — полная раскладка (см. architecture.md §7). Без неё на телефоне промах был 943 px. Тест проверяет точность перехода и падает без исправления.

## 4. Протокол замера

1. Production-сборка: `pnpm build && pnpm start`.
2. **HTTP/2.** Локальный `next start` отдаёт HTTP/1.1, а Lighthouse моделирует HTTP/1.1 как несколько соединений со своим «медленным стартом» и завышает время. Поставь локальный TLS-прокси HTTP/2 (`scripts/h2-proxy.mjs`, самоподписанный сертификат, Chrome с `--ignore-certificate-errors`). Vercel и нормальные хостинги отдают HTTP/2.
3. Два режима, по 5 прогонов, медиана и разброс:
   - `simulate` (по умолчанию, как PageSpeed Insights): прогон без замедления + модель (Slow 4G: 1,6 Мбит/с, 150 мс, процессор ×4);
   - `--throttling-method=devtools`: сеть и процессор замедляются на самом деле — ближе к реальному телефону.
4. Записывай «до → после» в одинаковых условиях: собери старую версию в `git worktree` и замерь так же.
5. Результаты и команды — в `docs/QA.md`.

```bash
npx lighthouse@13.5.0 https://localhost:3443/ --output=json --output-path=m1.json \
  --chrome-flags="--headless=new --no-sandbox --ignore-certificate-errors"
```

## 5. Как читать симуляцию

- Разбор LCP: `lcp-breakdown-insight` (TTFB, задержка загрузки, загрузка, задержка отрисовки) и список запросов, начатых до LCP в исходном прогоне.
- Модель включает в LCP все запросы, которые закончились до LCP в незамедленном прогоне, и все скрипты, которые **начали выполняться** до него. Если React начал гидратацию на пару миллисекунд раньше, чем кадр с фото попал на экран, вся гидратация засчитывается в LCP — отсюда разброс 2,25 / 2,7 с между прогонами. При реальном замедлении такого скачка нет.
- Предзагрузка шрифтов улучшает симуляцию, но при реальном замедлении CSS первого экрана делит канал со шрифтами, и первая отрисовка позже. Решай по реальному замедлению и фиксируй выбор в `QA.md`.

## 6. Что не сработало

- `experimental.inlineCss` в Next: LCP хуже (медиана 3,7 против 3,4 с), а документация не рекомендует его для продакшена. Откатили.
- Дальнейшее снижение: перенос карточек и контента в серверные компоненты (меньше RSC-данных и гидратации). Это большая переделка — делай по отдельной задаче.
